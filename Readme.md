# Project Dashboard

Веб-приложение для просмотра проектов и управления связанными задачами, разработанное в рамках тестового задания. Интерфейс выполнен в виде Dashboard с боковым меню и двумя таблицами AG Grid.

## Возможности

- Просмотр проектов с подгрузкой записей при прокрутке.
- Выбор проекта и просмотр его задач в связанной таблице.
- Добавление, редактирование и удаление задач с подтверждением удаления.
- Проверка данных формы и серверная валидация запросов.
- Сообщения об ошибках загрузки и повторная загрузка таблиц.
- Страницы «О проекте» и «Инструкции».
- REST API с полным CRUD для проектов и задач.

В интерфейсе проекты доступны для просмотра; их создание, изменение и удаление реализованы через API. При работе с задачей в форме автоматически используется выбранный проект. Перенос задачи в другой проект доступен через API, но не через форму.

## Технологии

- **Клиент:** React, TypeScript, Vite, React Router.
- **Интерфейс:** Ant Design, AG Grid Community.
- **HTTP-запросы:** Axios.
- **Сервер:** Node.js, Express, TypeScript.
- **Работа с БД:** Sequelize, SQL-запросы через `sequelize.query()`.
- **Валидация:** Zod.
- **База данных:** PostgreSQL 18.
- **Локальный запуск БД:** Docker Compose.

## Требования

- Node.js 24.x и npm.
- Docker с поддержкой Docker Compose; Docker должен быть запущен.
- Свободные порты `5432` для PostgreSQL, `3000` для API и `5173` для клиента.

## Установка и запуск

Склонируйте репозиторий или распакуйте его архив. Откройте терминал в корневой папке проекта — рядом с `package.json`, `init-db.sql` и `docker-compose.yaml`. Все команды ниже выполняются из этой папки.

### 1. Установите зависимости

```bash
npm ci
```

Проект использует npm workspaces: одна команда устанавливает зависимости клиента и сервера.

### 2. Создайте файл настроек

```bash
cp .env.example .env
```

Содержимое `.env` для локального запуска:

```dotenv
PG_USER=user
PG_PASSWORD=password
PG_HOST=127.0.0.1
PG_PORT=5432
PG_DATABASE=project_dashboard
PORT=3000
```

`PG_USER` и `PG_PASSWORD` используются и контейнером PostgreSQL, и сервером приложения. Значения из примера предназначены для локальной демонстрации. Файл `.env` исключён из Git.

Имя `project_dashboard` задано в `init-db.sql`: значение `PG_DATABASE` должно ему соответствовать. Клиентский прокси настроен на порт API `3000`; при изменении `PORT` также обновите `server.proxy` в `client/vite.config.ts`.

### 3. Запустите PostgreSQL

```bash
docker compose up -d db
docker compose logs -f db
```

При первом запуске на пустом томе контейнер автоматически выполнит `init-db.sql`: создаст базу `project_dashboard`, таблицы, ограничения, индекс и начальные данные. Дождитесь завершения инициализации и сообщения о готовности PostgreSQL принимать подключения. Нажмите `Ctrl+C`, чтобы выйти из просмотра логов; база продолжит работать.

Скрипт использует команды `psql` (`\set`, `\connect`) и рассчитан на первичную инициализацию. Повторно запускать его в уже созданной базе не нужно. При последующих запусках контейнера данные сохраняются в Docker volume, а скрипт повторно не выполняется. Изменение SQL-файла или учётных данных в `.env` не обновляет уже инициализированную базу автоматически.

### 4. Запустите сервер

В первом терминале:

```bash
npm run dev -w server
```

Сервер проверяет подключение к базе перед запуском. По умолчанию API доступен по адресу `http://localhost:3000/api`.

Проверить подключение к БД можно в браузере по адресу [http://localhost:3000/api/health](http://localhost:3000/api/health) или командой:

```bash
curl http://localhost:3000/api/health
```

Ожидаемый ответ:

```json
{
  "status": "Ok",
  "message": "database available"
}
```

### 5. Запустите клиент

Во втором терминале:

```bash
npm run dev -w client
```

Откройте [http://localhost:5173](http://localhost:5173). Vite перенаправляет запросы `/api` на сервер приложения. Отдельный `.env` для клиента не требуется.

### Остановка

Остановите клиент и сервер сочетанием `Ctrl+C` в соответствующих терминалах. Для остановки базы выполните:

```bash
docker compose stop db
```

Данные сохраняются. Для повторного запуска используйте `docker compose up -d db` и команды запуска сервера и клиента.

## Сценарий проверки

1. Откройте страницу «Проекты». Прокрутите верхнюю таблицу: новые записи загружаются блоками по 50 строк.
2. Выберите «Проект 1». В начальных данных у него 100 задач — можно проверить подгрузку во второй таблице.
3. Нажмите «Добавить», заполните название, стоимость, срок выполнения и приоритет. Созданная задача появится в таблице выбранного проекта.
4. Выберите задачу, нажмите «Изменить» и сохраните изменения.
5. Обновите страницу, снова выберите проект и убедитесь, что изменения сохранились.
6. Удалите созданную задачу, подтвердив действие в диалоговом окне.
7. Выберите «Проект 500»: в исходных данных у него нет задач. Проверьте пустое состояние и добавление первой задачи.
8. Откройте страницы «Инструкции» и «О проекте» через боковое меню.

В панели Network инструментов разработчика можно увидеть запросы с `limit=50` и меняющимся `offset`. Это серверная подгрузка, а не загрузка всех записей с последующим разбиением на клиенте.

## База данных

`init-db.sql` создаёт 500 проектов и 2500 задач.

Таблица `projects`:

- `id INTEGER` — первичный ключ.
- `title VARCHAR(150)` — название проекта.
- `budget NUMERIC(12,2)` — бюджет.
- `start_date DATE` — дата начала.
- `duration_days INTEGER` — длительность в днях.

Таблица `tasks`:

- `id INTEGER` — первичный ключ.
- `title VARCHAR(200)` — название задачи.
- `estimated_cost NUMERIC(12,2)` — стоимость.
- `due_date DATE` — срок выполнения.
- `priority INTEGER` — приоритет.
- `project_id INTEGER` — внешний ключ на проект.

Связь: `projects.id → tasks.project_id`, один проект содержит несколько задач. `ON DELETE RESTRICT` запрещает удалять проект, пока у него есть задачи. Индекс `tasks(project_id, id)` поддерживает выборку задач по проекту.

На уровне БД заданы ограничения: непустые названия, неотрицательные денежные значения, положительная длительность проекта и приоритет задачи от 1 до 5.

## REST API

Базовый адрес при локальном запуске: `http://localhost:3000/api`. Тела запросов передаются в JSON с заголовком `Content-Type: application/json`.

Проверка состояния:

- `GET /health` — проверка доступности БД.

Проекты:

- `GET /projects?limit=50&offset=0` — список проектов.
- `GET /projects/:id` — один проект.
- `POST /projects` — создание проекта.
- `PATCH /projects/:id` — частичное изменение проекта.
- `DELETE /projects/:id` — удаление проекта без задач.

Задачи:

- `GET /tasks?projectId=1&limit=50&offset=0` — список задач выбранного проекта.
- `GET /tasks/:id` — одна задача.
- `POST /tasks` — создание задачи.
- `PATCH /tasks/:id` — частичное изменение задачи.
- `DELETE /tasks/:id` — удаление задачи.

Для списков `limit` по умолчанию равен `50`, допустимы значения от `1` до `100`; `offset` по умолчанию равен `0`. Параметр `projectId` у списка задач необязателен: без него возвращаются задачи всех проектов. Ответ списка имеет форму `{ "items": [...], "total": 500 }`, где `total` — число записей с учётом фильтра, до применения пагинации.

Пример тела создания проекта:

```json
{
  "title": "Новый проект",
  "budget": "150000.00",
  "startDate": "2026-11-01",
  "durationDays": 30
}
```

Пример тела создания задачи для существующего проекта:

```json
{
  "projectId": 1,
  "title": "Подготовить документацию",
  "estimatedCost": "5000.00",
  "dueDate": "2026-11-15",
  "priority": 3
}
```

В `PATCH` передаётся хотя бы одно изменяемое поле. Денежные значения передаются и возвращаются строками с точкой в качестве десятичного разделителя; даты — строками `YYYY-MM-DD`. Название проекта ограничено 150 символами, задачи — 200. Стоимость и бюджет: от `0` до `9999999999.99`, не более двух знаков после точки. Приоритет задачи — целое число от `1` до `5`.

Успешное создание возвращает `201` и запись, чтение и изменение — `200`, удаление — `204` без тела ответа. Ошибки валидации возвращают `400`, отсутствующая запись — `404`, конфликт внешнего ключа — `409`. Недоступность БД на `/health` возвращает `503`.

## Проверки и сборка

```bash
npm run typecheck -w server
npm run typecheck -w client
npm run lint -w client
npm run build -w server
npm run build -w client
```

Сборки сохраняются в `server/dist` и `client/dist`. Собранный сервер запускается командой `npm run start -w server`; для него по-прежнему нужны `.env` в корне и запущенная БД. Используйте workspace-команды из инструкции: загрузка `.env` сервером зависит от рабочей директории.

Docker Compose в этом проекте запускает только PostgreSQL. Express не раздаёт клиентскую сборку. Для размещения приложения потребуется отдельно настроить раздачу `client/dist`, перенаправление `/api` на сервер и возврат `index.html` для клиентских маршрутов. Для локальной проверки полного приложения используйте запуск через Vite из раздела выше.

Автоматические тесты пока не добавлены; сценарий ручной проверки приведён выше.

## Возможные проблемы при запуске

- **Docker недоступен:** запустите Docker и повторите `docker compose up -d db`.
- **Порт занят:** остановите другое приложение, занимающее нужный порт. При изменении порта БД согласуйте публикацию порта в `docker-compose.yaml` и `PG_PORT`; при изменении порта API обновите прокси Vite.
- **Ошибка подключения к БД:** проверьте `docker compose ps`, логи базы и значения `.env`. Если том уже был создан с другими учётными данными, изменение `.env` само по себе не изменит пользователя и пароль в PostgreSQL.
- **База или таблицы отсутствуют:** проверьте логи первичной инициализации. `init-db.sql` выполняется автоматически только на пустом томе PostgreSQL.
- **Клиент открыт, но таблицы не загружаются:** проверьте `/api/health`, запуск сервера на порту `3000` и затем нажмите «Повторить» над таблицей.
